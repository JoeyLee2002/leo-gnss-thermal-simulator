## 发现摘要

| 严重性 | 问题 | 影响 |
|---|---|---|
| 高 | `componentModel('create', spec)` 将 `spec` 当作 network 传入 | 文档/接口声明的 create 入口不可用，工程接入会在创建阶段失败 |
| 高 | `inputFingerprint` 在导出时原样保留，导出文件无法再次导入 | 带来源指纹的 MAT/JSON 往返链路断裂，GUI 导出后的文件也可能无法重新载入 |
| 中 | 交换契约允许非标量 `uncertainty` 结构体 | 违反单记录语义；下游按标量访问时存在歧义/数据污染风险 |
| 中 | 温度依赖材料的表格曲线可在缺少 `temperatureK` 网格时注册 | 配置通过校验却必然在评估时失败，错误延迟到求解阶段 |
| 低 | 自定义材料注册可重复内置 ID，`list` 返回重复项 | 持久化 `persistent customMaterials` 被污染；列表和审计报告出现重名，且 `get` 静默优先内置值 |

## 详细证据与建议

### 1. 高：`componentModel('create', spec)` 接口漏洞

证据：[`src/+leotherm/componentModel.m:8-24`](../src/+leotherm/componentModel.m:8)。分支 `create` 在第 14–16 行把 `spec = varargin{1}`，但第 20–23 行仍以 `~isempty(varargin)` 为条件，把同一个 `varargin{1}` 作为 `network` 传给 `validateComponentModel`。因此最小合法部件：

```matlab
leotherm.componentModel('create', spec)
```

实际报错 `leotherm:InvalidComponent: network must provide nodeNames.`，而不是返回规范化部件。复现测试：`testComponentCreateActionTreatsSpecAsNetwork`。

建议：在 `create` 分支直接执行 `component = normalize(spec); component = leotherm.validateComponentModel(component); return`，或重写参数解析，使只有显式第三参数才作为 network。补充一个“create 成功且不需要 network”的正向测试。

### 2. 高：指纹模型导出后不可导入

证据：[`src/+leotherm/+io/importThermalModel.m:20-27`](../src/+leotherm/+io/importThermalModel.m:20) 将文件字节摘要与 `provenance.inputFingerprint` 严格比较；[`src/+leotherm/+io/exportThermalModel.m:1-20`](../src/+leotherm/+io/exportThermalModel.m:1) 导出前只校验模型并原样序列化，没有清除、重算或区分“源文件指纹”和“导出文件指纹”。只要输入模型带有合法的 64 位源指纹，导出会把该值写进新文件；新文件字节必然不同，重新导入即报 `leotherm:ThermalModelIOFingerprint`。复现测试：`testFingerprintSurvivesExportRoundTrip`。

建议：明确字段语义并实现一致策略：

* 若 `inputFingerprint` 只表示外部源文件，导出时应移除该字段或改存 `sourceFingerprint`，并在报告中返回新的 `outputFingerprint`；
* 若要求导出文件自校验，应采用两阶段写入（先序列化、计算摘要、再写入不参与摘要的 sidecar/字段）并记录算法；
* GUI 的 `saveThermalModel` 应复用同一策略，避免“导出成功、再导入失败”。

### 3. 中：交换契约放过非标量 `uncertainty`

证据：[`src/+leotherm/+io/validateThermalModel.m:33-34`](../src/+leotherm/+io/validateThermalModel.m:33) 只检查 `uncertainty` 是结构体或空值，没有 `isscalar`；而同一校验器对 `metadata`、`provenance` 明确要求标量（第 12、25 行）。因此 `model.uncertainty(1:2)` 可通过完整校验并写入 JSON/MAT。复现测试：`testExchangeValidatorAcceptsNonScalarUncertainty`。

建议：若契约是一条顶层不确定性记录，改为 `isstruct(...) && isscalar(...)`；若确实支持数组，应在文档中定义数组语义及版本化结构，并让所有 GUI/规范化消费者按数组处理。当前文档称 `uncertainty` 保存范围、分布、证据或假设，但没有数组语义，故应优先拒绝非标量。

### 4. 中：温度依赖曲线缺少网格仍可注册

证据：[`src/+leotherm/materialLibrary.m:117-130`](../src/+leotherm/materialLibrary.m:117) 对 `temperature_dependent` 材料仅校验曲线数组为正值；只有存在 `temperatureK` 时才检查长度和单调性。随后 [`materialLibrary.m:193-205`](../src/+leotherm/materialLibrary.m:193) 只有在 `numel(raw)>1 && isfield(material,'temperatureK')` 时才插值；缺少网格时直接返回整条向量，标量温度评估在第 210 行触发 `leotherm:InvalidMaterialProperty`。复现测试：`testTemperatureCurveWithoutGridRegistersButCannotEvaluate`。

建议：对表格曲线强制要求 `temperatureK` 且长度一致；或者将无网格数组定义为非法输入并在注册阶段抛出 `leotherm:InvalidMaterial`。函数句柄路径可继续允许无网格，但应验证输出尺寸、正值和温度范围。

### 5. 低：注册内置 ID 造成持久化重复项

证据：[`src/+leotherm/materialLibrary.m:33-35`](../src/+leotherm/materialLibrary.m:33) 的 `list` 将内置 ID 与全部 `customMaterials` 直接拼接；[`materialLibrary.m:46-51`](../src/+leotherm/materialLibrary.m:46) 只去重自定义列表，不检查内置 ID。实际 MATLAB 复现为：先执行 `a=leotherm.materialLibrary(); leotherm.materialLibrary('register',a(1)); leotherm.materialLibrary('list')`，返回列表中出现两个 `aluminum_6061`；而 `get` 在第 39–43 行静默优先内置版本。现有 `test_material_component_library/testBuiltInMaterialsAreReferenceOnly` 恰好会把内置材料注册进 persistent 状态，使后续测试/会话受到污染。

建议：注册时拒绝与内置 ID（或名称）冲突，或定义明确的覆盖策略并让 `list` 去重；增加测试确保重复注册不会改变解析结果、不会污染全局 persistent 状态，并提供测试清理入口（例如仅测试作用域的 reset）。

## 已检查且未发现直接缺陷的部分

现有契约测试覆盖了 schema、SI 单位、网络/体网格连通性和有限数值；MAT/JSON 基本往返、未知字段保留、指纹不匹配拒绝，以及 GUI 导入失败时保持旧模型不变均通过。GUI 工程热模型页的导入/导出控件和摘要标签在 Java 可用环境下均存在，相关测试通过。上述通过项不抵消“create 入口”和“指纹导出往返”两条高严重性问题，因为它们分别位于未覆盖的参数分支和带指纹的组合路径。

## 结论

审查时发现的 `create` 入口、指纹往返、非标量 `uncertainty` 和温度曲线网格问题已在 v0.14.0 修复，并由回归测试覆盖。材料库重名问题仍作为后续隔离/去重增强项保留。
